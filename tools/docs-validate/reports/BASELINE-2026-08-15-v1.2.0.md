## 2. The defect this baseline exists to record — `ADOPT-OBL-01b`

The v1.1.0 figures could not be reproduced. Re-running the committed v1.1.0 validator,
unmodified, at the same commit, in a clean checkout produced:

| | v1.1.0 committed report | v1.1.0 code, clean checkout |
| :--- | ---: | ---: |
| Errors | 13 | **8** |
| Warnings | 441 | **1,055** |
| `MMD-PARSE` | `FAIL`, 5 errors | **`PASS`, 0 errors** |
| Mermaid engine | `mermaid.parse` | **`structural`** |
| Diagrams not parsed | 0 | **612** |

### 2.1 Root cause

The Node harness resolved its dependencies with a bare `import 'mermaid'` and relied on
`NODE_PATH` to locate the package.

**`NODE_PATH` is honoured only by the CommonJS resolver. The ESM resolver ignores it.**

So `import 'mermaid'` threw `ERR_MODULE_NOT_FOUND` on any machine where the packages were
not in a parent directory of the temporary harness — which is every machine, because the
harness runs from `mkdtemp()` under `/tmp`. `_parse_with_node()` caught the failure,
returned `False`, and the validator fell through to the structural fallback.

Verified directly: with `NODE_PATH` set to a directory containing both packages, an
identical harness copied to a different directory still fails with
`Cannot find package 'jsdom'`.

### 2.2 Why this was worse than a missing feature

The fallback abstains on every diagram family except `graph`/`flowchart`. That abstention
is correct behaviour in isolation — but the run still reported:

```
[PASS] MMD-PARSE    enforces VAL-VIS-MERMAID-PARSE  measured=1998  errors=0
```

**A green check for work that was never done.** 5 genuinely broken diagrams — including
`ADOPT-OBL-02`'s `F{Mount]`, which is a known, recorded, unrepaired defect — were reported
as passing. This is the exact harm `VIS-728` warns about: output that trains its reader to
trust it while being wrong.

It also means the committed v1.1.0 baseline was produced in an environment that no CI run
could have reproduced. The `ci/docs-validate.yml` artefact installs Python only; had it
been installed, **CI would have reported 0 Mermaid errors indefinitely**.

### 2.3 Fixes

| Change | Effect |
| :--- | :--- |
| Harness resolves via `createRequire()` + `pathToFileURL()` rooted at the discovered `node_modules` | the authoritative engine actually loads |
| New check `MMD-ENGINE`, `ERROR` by default | degradation to the fallback is **fail-closed**, never silent |
| `engine_diagnostics` in the report | the *reason* for degradation is published, not swallowed |
| `require_authoritative` config switch | the opt-out is explicit and recorded, per `ADOPT-R1` |
| CI installs Node + `mermaid@11` + `jsdom`, then asserts the engine resolved | CI cannot silently run degraded |

No check was weakened. One was added, and it fails closed.

## 6. Validator self-test

**33 of 33 executed cases PASS**, in both environments:

| Environment | Executed | Passing | `UNSUPPORTED_BY_VALIDATOR` |
| :--- | ---: | ---: | ---: |
| With `mermaid` + `jsdom` | 33 | **33** | **0** |
| Without (clean checkout) | 33 | **33** | 3 |

The 3 unsupported cases are the ones that require a real grammar. They report their
dependency rather than passing vacuously — and `MMD-ENGINE-CLOSED` asserts that in
exactly that situation the corpus run **fails closed**.

New in v1.2.0: `MMD-ENGINE-REPORTED`, `MMD-ENGINE-CLOSED`, `MMD-ENGINE-OPT-OUT`,
`MMD-ENGINE-DIAG`, `MMD-FAM-NO-FALSE-POS`, `MMD-FAM-VERDICTS`.

## 7. Reproduction

```bash
npm install --no-save --no-audit --no-fund mermaid@11 jsdom
python3 tools/docs-validate/run-validator.py --self-test
python3 tools/docs-validate/run-validator.py --reports-dir tools/docs-validate/reports
```

Expected: self-test 33/33 PASS; corpus **FAIL — 13 errors, 443 warnings**, engine
`mermaid.parse`, `authoritative: true`.

Without the `npm install`, the corpus run reports **14 errors** — the 13 above plus
`MMD-ENGINE` — and Mermaid results are `UNSUPPORTED_BY_VALIDATOR`, not `PASS`.
